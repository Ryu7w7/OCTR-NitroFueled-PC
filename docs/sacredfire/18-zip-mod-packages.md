# ZIP packages extending XML patches (Windows proposal)

Contribution: tcosi, GPL-2.0-or-later. This adapts the declarative format developed
alongside venvs' Nitro Launcher ZIP support to the existing OCTR Windows launcher.
It is a proposed shared format, not an agreed universal modding standard. No
Nitro frontend or native executable is bundled here. Existing project credits
and patch authors remain unchanged. The read-only archive reader documents its
Crash-NST-Modding-Tool layout reference in its header.

## Player workflow

1. Copy a compatible ZIP into `mods/` next to the launcher.
2. On Patches, press Reload. A `ZIP mod: <id>` checkbox appears, initially off.
3. Enable compatible packages together and press Play. Fully exit/relaunch after
   changing package selection; in-game restart retains the selected package view.
4. Remove a ZIP and Reload to remove it. Its prepared cache cannot reactivate it.

Ordinary XML files in `patches/` retain their existing workflow. The generated
`patches/ZIP-Mod-Packages.xml` contains metadata-only checkboxes. Do not edit it.
ZIP components are composed privately at launch and checked together with all
selected stock/custom XML patches, including the online key and unlock patch.

`mod-packages/` contains checked payload caches, private game views, original
shader caches per exact engine hash, session logs and a separate mod save profile.
The normal game, saved INI and normal saves are never modified. On the first mod
launch, existing saves are copied into the mod profile; successful mod sessions
commit only to that profile, with backups. Disabling all packages returns to the
ordinary save profile. There is intentionally no implicit save merge in either
direction. Allow approximately a game-sized copy per distinct prepared selection.

Unknown shader inputs stop the launch. Missing shader inputs cause an unmodified,
offline setup session using the same engine; reach the main menu/required content
and accept the game's agreement yourself if asked. On Windows, setup requests
normal closure of its own verified child game when inputs stabilize, then starts
the selected packages using the configured online mode. No forced termination or
automatic retry loop is used. This bootstrapping skips the ZIP bridge to prevent
recursive setup. Foreign engine caches are not intentionally imported.

## Creator workflow

A ZIP contains `nitro-mod.json`, the generated `format-v2.required` marker and
declared payload files. One wrapper directory is supported. Keep a stable mod ID,
increment the version for updates, and keep one ZIP per ID in the library.
The creator tools require no game content to build a package:

```text
python scripts/package_mod_v2.py path/to/mod-source --output path/to/mod-1.0.0.zip
python scripts/package_mod_v2.py path/to/mod-source --validate
python scripts/inspect_mod_target.py --runtime path/to/portable --game path/to/own-game
python scripts/mod_packages.py --scan path/to/portable
```

The builder inventories every file and writes hashes, sizes and the old-loader
rejection marker. The inspector prints compatibility identifiers for the creator's
own installation. It does not certify a build: verify executable signatures,
assets and shaders before adding an engine hash to a released package.
Do not publish game files, original shader cache, saves, compiled game images or
credentials in this source repository. Real mod distributions remain separate.

Minimal manifest (hashes below are placeholders; use your tested installation):

```json
{
  "schemaVersion": 2,
  "id": "sample-mod",
  "name": "Sample mod",
  "version": "1.0.0",
  "author": "tcosi",
  "description": "A declarative package",
  "requiresCapabilities": ["xml-patches"],
  "compatibility": {
    "runtime_versions": ["TESTED_VERSION"],
    "runtime_sha256": ["EXACT_ENGINE_SHA256"],
    "eboot_sha256": ["EXACT_SUPPORTED_EBOOT_SHA256"],
    "online": "offline-only"
  },
  "files": [],
  "patches": ["patches/sample.xml"]
}
```

`files` is generated by the builder as `{file, sha256, bytes}` records. Every file
except the manifest must be listed, and undeclared extras fail validation.
XML must target CUSA13795, AppVer 01.21, AppElf eboot.bin and contain literal writes.
Unknown/misspelled fields and capabilities are rejected. Packages cannot run Python,
shell commands or installers, choose a save directory, replace eboot/system modules,
change online credentials or arbitrary environment variables.

| Capability | Manifest fields / operations |
| --- | --- |
| `xml-patches` | `patches`: declared XML file paths |
| `archive-assets` | `archive_asset`: PAK name, exact asset path/index, original/patched hashes, payload or same-size delta runs |
| `game-files` | `game_file`: relative target, original/patched hashes, declared payload; explicit null original hash for new files |
| `shaders` | `shader_file`, `shader_bytes`, `shader_position_scale`; targets confined to `cache/CUSA13795/` |
| `settings` | `settings`: allowlisted session-only INI overrides |
| `environment` | `environment`: BB_NEO, BB_FPS, BB_VBLANK_HZ, BB_DMEM_MB, BB_PREUPLOAD only |
| `constraints` | `constraints`: acceptable effective setting values |
| `dependencies` | `requires`: ID/version-range records; `conflicts`: incompatible IDs |
| `variants` | `variants` and optional `operationSets`: select exactly one static alternative |
| `variant-settings` | `variantSettings`: output/internal resolution domains and fallback defaults before selecting variants |

Complete PAK replacements can be declared as checked files under `archives/`.
Asset operations instead let disjoint changes within one PAK compose. A whole PAK
and an asset edit within that PAK conflict. Exact targets, shader targets and XML
write ranges also conflict. Dependency cycles and unsatisfied versions fail closed.

Example resolution declaration, requiring `variant-settings`:

```json
"variantSettings": {
  "output_res": {
    "default": "5120x1440",
    "allowed": ["2560x720", "3840x1080", "5120x1440", "7680x2160"]
  },
  "render_res": {
    "default": "1080",
    "allowed": ["480", "720", "1080", "1440", "1620", "2160"]
  }
}
```

Compatible saved preferences are preserved. Otherwise the enabled packages must
agree on a default within their shared supported domain. Selection happens before
`variants[].when` is evaluated; ordinary `settings` compiler-baseline overrides
are applied afterward. This is not monitor detection, and disabling the package
restores saved preferences. `nitro_format.py` is the executable validation contract;
the synthetic tests illustrate additional valid operations and failure cases.

## Scope and verification limits

This proposal extends Windows `run.py` and the existing Windows patch UI. It does
not change the renderer, native game loader, network protocol or Linux launcher.
The Linux run.sh path has not acquired ZIP support. Existing loose-file mods keep
their path; mixing an enabled loose-file mod with ZIP packages is rejected until
there is an explicit composition policy. ZIPs without schemaVersion 2 are reported
as unsupported rather than partially installed.

Exact engine/game hashes remain required. `online: "allowed"` is an author's
explicit declaration; the loader does not infer network compatibility from a
successful local patch compile. Current reserves/ultrawide examples were visually
tested in earlier isolated builds; the temporary v0.5 online adapter passed 49
non-overlapping XML writes with the online/unlock patches, but that does not
certify online races or rendering on current main. No real mod payloads accompany
this PR. Native Windows rebuild, gameplay and upstream CI remain separate checks.

Local source verification on Windows: all 40 new synthetic tests pass (ZIP
composition/lifecycle, XML skips/overlap, shaders and variant settings). The full
Python suite runs 151 tests: 116 pass, 32 require unavailable native components,
and the same three Linux-specific failures reproduce on the unmodified upstream
checkout (111 tests there). These are the bash overlay test and two Linux Vulkan
path tests. All Python scripts compile and `git diff --check` passes. `bash
build.sh --test` and the Windows native rebuild could not run because this host
lacks bash/MSYS2 and the compiler dependencies. This is a source-review draft,
not a newly certified binary release.

Caches are retained for reuse/diagnosis; removing/disabling a ZIP makes them inert.
There is no automatic cache garbage collector or automatic ZIP download/catalog.
Rollback of source changes is a normal Git revert; existing saves/settings need
no restoration. This contribution does not edit installed launchers.
